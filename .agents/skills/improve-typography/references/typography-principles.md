# Typography principles for websites

Adapted from Matthew Butterick's [Practical Typography](https://practicaltypography.com/). These are working judgments, not a demand that every page look like a book. Apply them to real text and screen sizes, compare alternatives, and let the purpose and audience decide. Numerical ranges are starting points, not accessibility limits or universal rules.

## Body text and measure

- **Size:** Start with the text people read most. Butterick suggests 15–25 CSS pixels for web body text; a font's apparent size depends on its design, so compare actual typefaces at actual sizes. Set a comfortable base in relative units and allow user preferences and zoom to work. Secondary text must remain readable; don't solve hierarchy merely by making it tiny.
- **Line height:** Butterick suggests 1.2–1.45 times the font size as a starting point. Adjust by eye for the face, line length, language, and content; more leading can help long lines and accessibility. Use unitless CSS `line-height` for inherited text. Check that ascenders, descenders, and diacritics don't collide. Headings often need a tighter line height than prose.
- **Line length and margins:** Aim initially for an average of 45–90 characters including spaces in continuous prose. Measure representative rendered paragraphs, not a single line: CSS `ch` is an approximation, not an actual character count. Long lines make it harder to find the next line; very narrow lines make a ragged, choppy block. Limit the prose measure, maintain breathing room at viewport edges, and adjust measure and size together. Navigation, tables, and app layouts need their own widths.
- **Paragraphs:** Use either space between paragraphs or first-line indentation to mark ordinary paragraph boundaries; combining prominent versions of both is usually redundant. For spaced prose, start around 0.5–1em and tune it so paragraphs are distinct but connected. If using indents, start around 1–4em, with little or no paragraph gap; the first paragraph after a heading need not be indented. Use CSS spacing rather than empty paragraphs or repeated breaks.

## Alignment, hierarchy, and layout

- **Alignment:** Start-align sustained prose to give the eye a consistent return edge, respecting writing direction. Centering can suit a short title, label, or deliberate composition, but multi-line centered paragraphs have two uneven edges and are harder to scan. Check line breaks at several widths; avoid hard breaks that only work at one viewport.
- **Justification and hyphenation:** Browser justification can produce large word spaces, especially in narrow columns. Prefer start alignment unless justification serves the design and has been checked. If justified, enable appropriate language-aware hyphenation, set the correct `lang`, and inspect browser and language support and the resulting word spaces. Hyphenation is optional for ragged text; generally avoid it in headings. Don't insert misleading hyphens into URLs, email addresses, code, or identifiers; allow safe wrapping instead.
- **Headings:** Make the structure understandable before styling it. Limit unnecessary levels, use semantic heading order, and give headings consistent roles. Start with space, modest size or weight changes, and alignment; avoid stacking all caps, bold, underlines, color, and oversized type on the same heading. Usually give more space before a heading than after it so it belongs to what follows. Heading text should wrap naturally without colliding or leaving awkward fragments. Distinctive display type may be appropriate when the page calls for it.
- **Whitespace and grids:** Use margins, alignment, and spacing to clarify groups and establish a foreground/background relationship. Use a simple grid to relate elements and widths; a grid is a guide, not proof of a good layout. Asymmetry can be useful. Keep navigation and decoration from overpowering the primary content. Compare small visual adjustments in context instead of relying on a prescribed ratio.
- **Columns:** Avoid long newspaper-style flowing columns on scrolling screens where readers must repeatedly scroll back up. Multiple columns can suit short lists or content that fits within a viewport. Collapse or reorganize them when space is narrow and retain logical reading order.
- **Rules and borders:** Try whitespace and alignment before enclosing every element. Use rules where they clarify grouping or comparison, and keep them visually quieter than the information. Don't remove boundaries needed to recognize controls, focus, or separate dense data.
- **Pagination:** For print styles or paginated output, check headings stranded at page bottoms and paragraphs split across pages; use break controls or widow/orphan controls where supported and useful. On a scrolling page, focus instead on awkward short lines and heading wraps; do not force brittle nonbreaking text across all viewport sizes.

## Text formatting and detail

- **Fonts and mixing:** Choose a face that fits the voice and holds up in paragraphs, UI labels, required languages, and weights. Prefer proportional type for sustained prose; monospace is useful for code, aligned literals, and purposeful design. One family can provide sufficient contrast; use additional families for distinct, consistent roles, and test their apparent size and weight together. Examine real font variants and licensing, not just family names.
- **Size and emphasis:** Choose the smallest visible distinction that creates the needed hierarchy. Use bold or italic sparingly; combining them or emphasizing entire paragraphs can dilute their effect. Italic is useful for quiet emphasis, bold for stronger emphasis. Preserve semantic emphasis in markup. Avoid underlining ordinary emphasis, which can be mistaken for a link; keep inline links recognizable, commonly with an underline.
- **Caps and tracking:** Reserve all caps for short labels or other intentional uses rather than sustained reading. Butterick suggests roughly 0.05–0.12em extra letterspacing for all caps and small caps; test the actual font and language, especially at small sizes. Normal lowercase generally needs little or no added tracking. Avoid aggressive negative tracking that closes counters or makes letters collide. Do not apply Latin tracking rules indiscriminately to scripts where spacing disrupts shaping.
- **Kerning and OpenType:** Let the font's kerning and shaping work; check prominent headings for conspicuous gaps. Use real small caps, not scaled-down capitals, when the font supports them. OpenType features vary by font and browser: verify actual output and fallback instead of assuming a feature exists. Avoid disabling required script shaping or ligatures globally.
- **Numerals:** Use tabular figures when digits must line up in columns or changing values; use proportional figures where natural spacing matters in running text. Lining figures fit uppercase contexts; oldstyle figures can blend into lowercase prose when supported and appropriate. Test `font-variant-numeric` with the chosen font, including fallback.
- **Color:** Use contrast and restraint to establish importance. Body, secondary text, links, and disabled states need to remain distinguishable against their actual backgrounds in each theme. Avoid using hue alone for meaning; ensure links and focus remain identifiable. Check computed contrast and also inspect the rendered result, especially small or thin text.
- **Punctuation and content:** In authored prose, use appropriate quotation marks, apostrophes, dashes and nonbreaking spaces where they improve reading. Preserve the meaning and exact bytes of code, identifiers, URLs, user content, and data; account for language-specific conventions. Avoid blanket typographic substitutions or text transformations that change meaning.

## Common structures

- **Lists:** Use semantic `<ul>` and `<ol>` with actual list items, not manually typed bullets or numbers. Align wrapped lines with the item text; give markers and items enough room, and make spacing match whether the items are short labels or paragraphs. Keep nested levels intelligible.
- **Block quotations:** Use semantic `<blockquote>` and distinguish the block with spacing and/or a modest indent. Maintain a useful measure on narrow screens; don't shrink quotation text so far that it becomes difficult to read. A block quotation's presentation already signals quotation, so surrounding quotation marks are often redundant; respect supplied content and language conventions.
- **Tables:** Use semantic table headers for tabular data and preserve their relationships. Give cells adequate padding and align comparable values consistently; tabular figures help numeric columns. Remove unnecessary full-cell borders if whitespace and a few rules provide enough structure. Test long labels, narrow viewports, scrolling and keyboard access without hiding data. Use CSS grid or flexbox for ordinary page layout rather than presentational data tables.
- **Links and addresses:** Make links identifiable in context and provide visible keyboard focus. Allow long visible URLs and email addresses to wrap without adding characters to the address or breaking the destination. Preserve meaningful link text and accessible names.
